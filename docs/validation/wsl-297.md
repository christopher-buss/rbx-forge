# WSL release evidence for specification 297

Release approval: **open**. ADR 0009 remains proposed. The current public
release is v2.3.0; it predates WSL support. No minimum WSL release version is
assigned by this validation. The maintainer records the actual first release
version and requires it on both sides before publication.

`7aa0ac4f3aead64cddcf6999a9b32b61f026903c` on 2026-11-16. The working changes
add the WSL real-Studio form, packaging gate instructions, CI capability probe
and Content capture compatibility. The validation includes the implementation
diff on that base; the final implementation commit records the exact files.

omitted from this document.

## Reproduced drvfs limitation

`probe-rojo-drvfs.json` starts genuine Linux Rojo 7.7.1 on a disposable project,
reads its actual msgpack API, changes a Configuration attribute in the served
project, and reads it again. On drvfs no filesystem event arrives, the message
cursor stays zero and Rojo serves the initial value. The identical
`probe-rojo-ext4.json` run on the scratch ext4 image receives a change event,
advances the cursor and serves the updated value. This independently explains
the real session captures' empty endpoint attributes; snapshot captures pass.

Rojo's
[filesystem backend](https://github.com/rojo-rbx/rojo/blob/v7.7.1/crates/memofs/src/std_backend.rs)
uses native notify events and its current CLI exposes no polling flag. A
supported publication/reload strategy for the generated capture metadata is
required before the drvfs cell can pass. No test-only refresh or weaker capture
assertion is used to conceal it. Menu-save timeouts also remain a failing gate;
the successful narrow rerun does not establish that they are fixed.

## Outstanding release evidence

All four cells in [the gate](../wsl-release-gate.md) need a final passing
record. The first real drvfs/NAT run fails. The ext4 cells, mirrored cells,
forwarding-disabled negative check, remaining terminal-loss and
uncertain-command matrix, and cross-side actual-process exclusion are not
certified here.

A disposable ext4 image is created only inside the approved scratch root. Its
mount under drvfs translates through `wslpath -w` to a Windows drive path, which
does not expose that nested ext4 mount to Studio. It does not establish the
normal ext4-to-WSL-UNC gate. Running the normal ext4 cell needs an approved
Linux-file-system fixture root. No fixture is moved into a user's project.

Switching to mirrored networking or disabling NAT forwarding requires
coordinating live Ubuntu and Docker workloads and restarting WSL. That work is
left for the parent/maintainer after those workloads are safe to interrupt. The
Windows 2025 hosted results below prove VM execution and report a failing
fixture lifecycle. All standard OS, ARM64 and other-user CI jobs pass in the
corrected run. No passing release gate or ADR acceptance is claimed.

## Hosted CI

The
[first hosted run](https://github.com/christopher-buss/rbx-forge/actions/runs/43818670135)
checks implementation commit `fcec3cab86095cd74069e093198a02d330925c90`. All
eight native targets, all three other-user jobs, and Windows standard checks
pass. Linux and macOS unit checks expose a non-executable helper fixture; the
follow-up commit gives that fixture mode 0755, without changing the locator's
executable check. A native Linux run on the scratch ext4 image passes all 21
node-seams cases after the fix (with the native-Linux unit form's WSL
environment unset).

The Windows 2025 capability job retains artifact `wsl-capability-windows-2025`,
image `win25-vs2026`, version `20261103.298.1`, x64. Ubuntu installs
successfully as WSL2, but an unconditional version conversion returns
`WSL_E_VM_MODE_INVALID_STATE` because it is already version 2. The first report
therefore says `provisioning-failed`; it proves no running VM. The follow-up
probe requests conversion only for a listed version-1 distro and still requires
successful Linux execution. Its corrected local helper lifecycle passes
(`capability-local-final/report.json`). The corrected
[hosted run](https://github.com/christopher-buss/rbx-forge/actions/runs/43822088884)
checks `70f4c5cec54e45d2cee9640a8a68ab90ed7b444d`. All three standard OS checks,
all eight native targets and all three other-user jobs pass. The first
capability attempt reaches its 180-second provisioning timeout with no output;
that report remains `provisioning-failed`. A fresh-runner retry proves the VM
and helper handshake, then fails the actual fixture launch with
`operation_failed: detached launch unavailable`. The job remains failed after VM
success; no unsupported-capability skip conceals it. Its report is retained at
`capability-hosted-retry/report.json`, image `win25-vs2026` / `20261103.298.1`,
WSL 3.0.3.0 and kernel 6.18.54.1. The hosted result establishes VM availability
and a post-handshake detached-launch limitation, not real Studio support in CI.

`wsl-menu.log` reproduces an uncertain repeated hidden save through a
transparent trace of the actual helper. Windows and Linux metadata agree before
the request; the original request receives no reply before its deadline, and the
file changes by the time the CLI reports `save_failed` with reason `unknown`.
The subsequent native-phase diagnostic run passes and does not establish a fix.
Temporary Rust trace edits are restored; only scratch diagnostic binaries retain
them. No uncertain save is repeated by forge.

The committed WSL suite also covers terminal loss for a hidden snapshot. The
final three-case run (`wsl-final-terminals.log`) passes the session owner loss,
snapshot Lighting watcher owner loss plus save, and genuine lost-save-reply
cases (3 pass, 15 unselected). The launcher returns the owned Windows relay's
PID and start time together, and helper control verifies that identity before
closing it. This strengthens cleanup without targeting another terminal.
