release is v2.3.0; it predates WSL support. No minimum WSL release version is

## Reproduced drvfs limitation

`probe-rojo-drvfs.json` starts genuine Linux Rojo 7.7.1 on a disposable project,
reads its actual msgpack API, changes a Configuration attribute in the served
project, and reads it again. On drvfs no filesystem event arrives, the message
cursor stays zero and Rojo serves the initial value. The identical
`probe-rojo-ext4.json` run on the scratch ext4 image receives a change event,
advances the cursor and serves the updated value. This independently explains
the real session captures' empty endpoint attributes; snapshot captures pass.

Rojo's
[filesystem backend](https://github.com/rojo-rbx/rojo/blob/v7.7.1/crates/memofs/src/std_backend.rs)
uses native notify events and its current CLI exposes no polling flag. The
production wrapper now publishes a secret bootstrap endpoint before Rojo starts.
The managed plugin resolves its actual identity only against its connected Rojo;
no notification or test-only reload is required. Patch version 5 recognizes
known versions 2–4. The shipped Lua harness covers valid, foreign and delayed
identity responses. Menu-save timeouts also remain a failing gate; the
successful narrow rerun does not establish that they are fixed.

## Outstanding release evidence

All four cells in [the gate](../wsl-release-gate.md) need a final passing
record. The first real drvfs/NAT run fails. The ext4 cells, mirrored cells,
forwarding-disabled negative check, remaining terminal-loss and
uncertain-command matrix, and cross-side actual-process exclusion are not
certified here.

A disposable ext4 image is created only inside the approved scratch root. Its
mount under drvfs translates through `wslpath -w` to a Windows drive path, which
does not expose that nested ext4 mount to Studio. It does not establish the
normal ext4-to-WSL-UNC gate. Running the normal ext4 cell needs an approved
Linux-file-system fixture root. No fixture is moved into a user's project.

Switching to mirrored networking or disabling NAT forwarding requires
coordinating live Ubuntu and Docker workloads and restarting WSL. That work is
left for the parent/maintainer after those workloads are safe to interrupt. The
Windows 2025 hosted results below prove VM execution and report a failing
fixture lifecycle. All standard OS, ARM64 and other-user CI jobs pass in the
corrected run. No passing release gate or ADR acceptance is claimed.
